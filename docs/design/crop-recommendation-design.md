## 1. Рекомендоване рішення та його межі

### 1.1 Коротко

Пропонуємо **послідовний відбір + ранжування за шарами з інтервальною оцінкою**. Модель навчати не потрібно.

1. **Генерація кандидатів.** З каталогу підтримуваних культур і варіантів (озимий/ярий) беремо ті, що мають дані GAEZ, правила для регіону та посівне вікно, яке перетинається з горизонтом рекомендації.
2. **Жорсткі бар’єри (gates).** Культуру виключаємо лише за надійною підставою: посівне вікно вже неможливо виконати, підтверджена несумісність сівозміни або підтверджена непридатність за GAEZ без суперечливих локальних даних. Ще одна підстава — явне обмеження користувача.
3. **Агрономічна оцінка як інтервал** `[lo, mid, hi]`:
   `Agro = A_gaez × M_rot × M_wx`, де
   - `A_gaez` — нормований індекс придатності GAEZ;
   - `M_rot` — обмежений множник сівозміни;
   - `M_wx` — обмежений множник **аномалії** поточних умов посіву відносно норми.

   Пропуск даних **розширює інтервал**. Позицію визначає нижня межа, тому пропуск ніколи не покращує місце культури.
4. **Агрономічні яруси.** Кандидати, чиї інтервали перекриваються з лідером ярусу, вважаються агрономічно нерозрізненими. Культура з нижчого ярусу ніколи не стоїть вище культури з вищого.
5. **Економіка лише всередині ярусу.** Якщо для культур ярусу є ціна, урожайність і витрати, їх упорядковуємо за сценарною маржею. Культури без повної економіки зберігають свої агрономічні місця.
6. **Перевірка стійкості.** Перераховуємо рейтинг на детермінованій сітці збурень: параметри множників, рівень агротехнологій, кліматичний період GAEZ, цінові сценарії, витрати. Для кожної культури повертаємо частку сценаріїв, у яких вона в топ-5, і діапазон її місць.
7. **Пояснення.** Кожен крок пише структуровану подію в журнал рішення (decision trace). Текст для користувача формується з шаблонів за цими подіями, без LLM.

### 1.2 Що система стверджує, а що — ні

| Система стверджує | Система НЕ стверджує |
|---|---|
| Культура агрономічно придатна для клімату й ґрунтів **комірки GAEZ** за заданих агротехнологій | Що поле в межах комірки має ті самі ґрунти |
| Культура сумісна з відомою історією поля за версією правил X | Що врожай буде отриманий |
| Сценарна виручка / маржа за наданих урожайності, цін і витрат | Прибуток, фактичний дохід або ціну після збирання |
| Потенціал GAEZ (attainable yield) за припущень моделі GAEZ | Прогноз фактичної врожайності |
| Зведений бал і стійкість рейтингу | Ймовірність успіху |

### 1.3 Режими результату

| Режим | Коли | Що повертаємо |
|---|---|---|
| `FULL` | Агрономія + повна економіка хоча б для частини кандидатів ярусу 1 | Рейтинг з економічним упорядкуванням усередині ярусів |
| `AGRO_ONLY` | Немає цін, урожайності або витрат | Агрономічний рейтинг; виручку, якщо є, показуємо окремо як довідку, без впливу на місце |
| `LIMITED` | Неповне покриття GAEZ, немає історії тощо | Рейтинг з явними обмеженнями та ширшими інтервалами |
| `NEEDS_INPUT` | Бракує входу, який змінює рішення (§9) | Перелік питань і, за можливості, умовний попередній рейтинг |
| `ABSTAIN` | Даних недостатньо для обґрунтованої рекомендації | Причини відмови |

| Етап | Обсяг |

## 2. Критичні припущення й необхідні входи

### 2.1 Обов’язкові входи

| Вхід | Навіщо | Без нього |
|---|---|---|
| Геометрія поля + CRS | Отримання GAEZ і погоди | `ABSTAIN` |
| `as_of_date` — дата формування рекомендації | Посівні вікна, межа даних «до цієї дати» | `NEEDS_INPUT` |
| `target_season` — наприклад, урожай 2027 (посів осінь 2026 + весна 2027) | Визначає набір озимих і ярих кандидатів | `NEEDS_INPUT` |
| Регіон (обчислюється з геометрії) | Посівні вікна та правила | Якщо для регіону немає правил і вікон — `ABSTAIN` |

### 2.2 Бажані входи від користувача

| Вхід | Вплив | Поведінка за замовчуванням |
|---|---|---|
| Рівень агротехнологій (`high`/`low`) | Вибір шару GAEZ (HRLM vs LRLM). Різниця може бути великою | Припущення `high`, прапорець; LRLM включаємо в сітку стійкості. Якщо топ-5 змінюється — `NEEDS_INPUT` |
| Зрошення (так/ні, для яких культур) | HILM vs HRLM | `rainfed` |
| Поточна культура та очікувана дата збирання | Посівне вікно для озимих | Якщо невідомо — озимі кандидати отримують статус `conditional`, без виключення |
| Витрати на гектар за культурами | Сценарна маржа | Без них економіка не впливає на місце |
| Очікувана урожайність (історія господарства) | Сценарна виручка | Регіональна статистика, якщо підключена; інакше економіки немає |
| Обмеження: немає техніки або контракту, заборона культури | Бар’єр `USER_CONSTRAINT` | — |
| Контрактна ціна | Пріоритетніша за ринкову | — |

### 2.3 Критичні припущення

1. **A1.** Поле — орні землі. Тому основний шар GAEZ — варіант «поточні орні землі в комірці» (SUX/SCX), а не «вся комірка» (§6.6).
2. **A2.** GAEZ описує середній клімат періоду, а не конкретний сезон. Базовий період — `HP0120` (2001–2020, AgERA5). `FP2140` (2021–2040, ансамбль GCM) — лише для перевірки чутливості.
3. **A3.** Правила сівозміни й посівні вікна наповнює і підписує агроном. У документі вони є лише прикладами структури.
4. **A4.** Таблиця цін — зовнішня й готова. Ми її нормалізуємо, але не наповнюємо.
5. **A5.** Супутникові індекси вже пораховані, мають маски хмар і статистики в межах поля.

**Межі модулів.**
- `adapters/` знають формати зовнішніх джерел і нічого не знають про ранжування.
- `features/` перетворюють сирі дані на ознаки з одиницями, якістю та provenance.
- `ranking/` працює лише з `FieldFeatureSnapshot` + `RecommendationRequest` + версією правил. Це чиста функція без мережевих звернень. Завдяки цьому вона детермінована й придатна для бектесту.

## 4. Джерела та роль кожного показника

### 4.1 Перевірені відомості про GAEZ v5 [ПЕРЕВІРЕНО]

**Доступ.**
- Публічний бакет `gs://fao-gismgr-gaez-v5-data/DATA/GAEZ-V5/MAPSET/<VARIABLE>/<FILE>.tif`.
- HTTPS-доступ: `https://storage.googleapis.com/fao-gismgr-gaez-v5-data/DATA/GAEZ-V5/MAPSET/...`.
- Поряд із кожним `.tif` лежить `.json` з вимірами шару.
- Довідники вимірів: `DATA/GAEZ-V5/DIMENSION/GAEZ-V5.<DIM>.csv` (CROP-RES05, CROP-RES02, PERIOD, CLIM, SSP, WSIM-RES05).

**Шаблон імені (тема 4, RES05):** `GAEZ-V5.<VAR>.<PERIOD>.<CLIM>.<SSP>.<CROP>.<WSIM>.tif`.
Приклад, перевірений читанням файлу: `GAEZ-V5.RES05-SXX.HP0120.AGERA5.HIST.WHE.HRLM.tif`.

**Періоди:**
- `HP8100` — 1981–2000;
- `HP0120` — 2001–2020;
- `FP2140`, `FP4160`, `FP6180`, `FP8100` — майбутні 20-річні періоди.

**Кліматичні дані та сценарії:**
- джерела `CLIM`: `AGERA5` (історичні періоди), 5 GCM (`GFDL-ESM4`, `IPSL-CM6A-LR`, `MPI-ESM1-2-HR`, `MRI-ESM2-0`, `UKESM1-0-LL`), `ENSEMBLE`;
- сценарії `SSP`: `HIST`, `SSP126`, `SSP370`, `SSP585`.

**Водозабезпечення та агротехнології (`WSIM`):**

| Код | Значення |
|---|---|
| `HILM` | Зрошення, високий рівень |
| `HRLM` | Богара, високий рівень |
| `LILM` | Зрошення, низький рівень |
| `LRLM` | Богара, низький рівень |

Опис вимірів уточнює: AWC 200 мм/м.
У лістингу файлів майбутніх періодів видно лише `HILM` і `HRLM`. Чи немає `L*LM` для майбутніх періодів взагалі — [НЕ ПЕРЕВІРЕНО повністю].

- Масштаб 1,0, зміщення 0.

| Клас | Значення |
|---|---|
| 1 | SI > 85, Very high |
| 2 | SI > 70, High |
| 3 | SI > 55, Good |
| 4 | SI > 40, Medium |
| 5 | SI > 25, Moderate |
| 6 | SI > 10, Marginal |
| 7 | SI > 0, Very marginal |

**Одиниці врожайності.**
- Здебільшого кг **сухої речовини** на гектар.
- Винятки: деякі олійні культури (у перерахунку на олію), цукрові культури (у перерахунку на цукор), бавовник (у перерахунку на волокно).
- Таблиця вологості для перерахунку на товарну продукцію (вікі, модуль VII):
  - пшениця, ячмінь, соняшник — 13 %;
  - кукурудза — 14 %;
  - соя — 9 %;
  - ріпак — 8 %;
  - зернобобові — 10 %;
  - цукровий буряк — «14 % sugar».

**Культури RES05**, що стосуються помірного клімату (довідник `CROP-RES05`): `WHE`, `BRL`, `RYE`, `OAT`, `TRI`, `BCK`, `MZE`, `MZS`, `SFL`, `SOY`, `RSD`, `PEA`, `CHK`, `PHB`, `SUB`, `WPO`, `FLX`, `SRG`, `FML`, `ALF`, `CAM`, `ONI`, `CAB`, `CAR`, `TOM`.

#### Критична знахідка: озимі та ярі варіанти

- У **модулі V (RES05)** пшениця, ячмінь, ріпак і жито мають **по одному коду** (`WHE`, `BRL`, `RSD`, `RYE`) без поділу на озимі та ярі. Додаток 4-1 описує модуль II з підтипами («best sub-type», spring, hibernating).
- У **модулі II (RES02, агрокліматичний потенціал без ґрунтів)** підтипи є: `SWHE`, `HWHE`, `WHEA` («best»), `SBRL`, `WBRL`, `SRAP`, `WRAP`, `SRYE`, `WRYE`, `TMZE` тощо.
- Підписи підтипів суперечать одне одному:
  - у `CROP-RES02.csv`: `HWHE` = «Highland wheat (tropics)», `WWHE` = «Winter wheat (sub-tropical and tropical highland)»;
  - у Додатку 4-1 (Excel): `HWHE` = «Wheat, hybernating types».
- Вибірка для вікна 49–50° пн. ш., 30–31° сх. д., шар `RES02-YLD`, HP0120, HRLM:
  - медіана `WHEA` = медіані `SWHE` (≈6496);
  - `CBD` (день початку циклу) для `WHEA` ≈ 89 (кінець березня), для `HWHE` ≈ 86;
  - файл `WWHE` для цього періоду за очікуваною назвою не знайдено (404).

**Висновок.** Без підтвердження від FAO/IIASA **не можна трактувати RES05 `WHE` як оцінку саме озимої пшениці**: у цьому вікні «найкращим» підтипом, імовірно, обрано ярий. Варіант `RES02-IDX` («Selected LUT sequence number») може показати, який LUT обрано. Рішення для системи:
- Озимі й ярі варіанти — окремі кандидати.
- Їхня GAEZ-оцінка береться з батьківського коду RES05 з прапорцем `gaez_variant_match = parent_crop`.
- Це знижує рівень доказовості, а не бал.
- Розрізнення варіантів у V1 забезпечують посівні вікна, сівозміна та погодні умови посіву, а не GAEZ.

## 5. Детальний механізм ранжування

### 5.1 Що таке «найкраща культура»

**Найкраща культура** — та, що для цього поля й цієї дати:
1. Не має **підтверджених** підстав для виключення.
2. Належить до найвищого **агрономічного ярусу**. Ярус — група культур, агрономічні оцінки яких нерозрізненні з урахуванням невизначеності.
3. Усередині ярусу має кращу **сценарну маржу**, якщо економіка доступна.
4. Тримає свою позицію за розумних збурень параметрів, тобто стійка.

Основна ціль — **лексикографічна**: (ярус ↑, [маржа ↑ у межах ярусу], агробал ↑, ризик ↓, якість даних ↑).
Обрано її замість зваженої суми, бо зважена сума компенсаторна: висока ціна могла б «викупити» низьку придатність, а ваги між гривнями й індексом придатності не мають обґрунтування.

### 5.2 Порівняння способів поєднання

| Спосіб | Плюси | Мінуси | Рішення |
|---|---|---|---|
| Зважена сума нормованих критеріїв (MCDA/TOPSIS) | Простий, звичний | Компенсаторний; ваги довільні; змішує одиниці; ціна перекриває непридатність; пропуски важко обробити чесно | Ні |
| Чисто економічна оптимізація (макс. маржа) | Зрозуміла ціль | Потрібні урожайність, витрати й ціна після збирання, яких здебільшого немає; ігнорує агроризик | Ні (лише як режим усередині ярусу) |
| **Послідовний відбір + інтервальні яруси + економіка в ярусі** | Некомпенсаторний між ярусами; пропуски розширюють інтервали; пояснення прямо відтворює логіку | Межі ярусів чутливі до ширини інтервалів, тому потрібна перевірка стійкості | **Так, V1** |
| Сценарне економічне ранжування (очікувана маржа за сценаріями) | Враховує невизначеність цін і врожаю | Потрібна модель урожаю | P2, всередині ярусів |

### 5.4 Крок 2 — жорсткі бар’єри (виконуються першими)

Порядок бар’єрів: від найдешевших і найнадійніших до найдорожчих. Кожен бар’єр повертає `PASS`, `EXCLUDE(reason, evidence)` або `CONDITIONAL(reason, what_to_confirm)`.

| ID | Умова виключення | Вимога до доказів | Якщо доказів недостатньо |
|---|---|---|---|
| G1 `USER_CONSTRAINT` | Користувач явно виключив культуру або вказав відсутність критичної умови (наприклад, техніки для цукрового буряка) | Явний вхід | — |
| G2 `SOWING_WINDOW` | `as_of + min_lead_days > window.latest` (вікно минуло) **або** `predecessor_harvest_date + prep_days > window.latest` | Дата збирання з надійністю ≥ `medium`: факт або план користувача | `CONDITIONAL`: «підтвердьте дату збирання попередника» |
| G3 `ROTATION_INCOMPATIBLE` | Правило з `effect: incompatible` спрацювало | Правило `status: approved`; записи історії, від яких воно залежить, мають надійність ≥ `medium` | Перетворюється на `discouraged_strong` + запит |

| G5 `NO_EVALUABLE_DATA` | Валідне покриття GAEZ < 0,5 | — | Культура переходить у «не оцінено» (не в рейтинг і не в «виключено») |

### 5.5 Крок 3 — агрономічна оцінка як інтервал

Для кожного кандидата, що пройшов бар’єри:

```
Agro.lo  = A.lo  × M_rot.lo  × M_wx.lo
Agro.mid = A.mid × M_rot.mid × M_wx.mid
Agro.hi  = A.hi  × M_rot.hi  × M_wx.hi
```

Множення обрано тому, що поправки сівозміни й погоди пропорційно масштабують придатність. Культура з низьким `A` не може піднятися вище за `A × max_bonus`.

#### 5.5.1 `A_gaez` ∈ [0, 1] — придатність GAEZ

- `A.mid = SUX_field / 10000`. `SUX_field` — середнє з вагами площі перетину для вибраного `WSIM` у період `HP0120` (§6).
- `A.lo` і `A.hi` — мінімум і максимум серед:
  - значень окремих комірок, що покривають ≥ 10 % поля;
  - `SXX30AS/10000` (якщо є й відрізняється від 5′; для 30″ немає варіанта SUX, тому використовуємо SXX30AS, бо в 30″ комірці частка неорних земель менша);
  - `SUX` за `FP2140 / ENSEMBLE / {SSP126, SSP370, SSP585}`.
- Якщо валідне покриття від 0,5 до 0,8: `A.lo` додатково зменшуємо до мінімального значення серед усіх сусідніх комірок у буфері 1 комірки [ІНЖ. МОДЕЛЬ].
- Якщо `SUX` = NoData, а `SXX` валідне (у комірці за GAEZ немає орних земель): `A.mid = SXX/10000`, прапорець `gaez_fallback_all_land`, інтервал `[0.8·A.mid, A.mid]` [ІНЖ. МОДЕЛЬ].

**Чому не додаємо окремих погодних або ґрунтових штрафів.** `SUX` уже містить терморежим, водний баланс середнього клімату, агрокліматичні обмеження (шкідники, хвороби, придатність до обробітку) і ґрунтово-рельєфні обмеження (модулі II–V). Повторний штраф за «посушливий регіон» був би подвійним врахуванням.

#### 5.5.2 `M_rot` — множник сівозміни [ІНЖ. МОДЕЛЬ]

Правило дає **категорію наслідку**, а не число. Число береться з окремої конфігурації `effect_multipliers.yaml`, яка має версію та статус калібрування:

| Категорія | Початкове значення (заглушка, потребує погодження) | Значення |
|---|---|---|
| `favorable` | 1,05 | Сприятливий попередник |
| `neutral` | 1,00 | Правило не спрацювало, а історія повна |
| `discouraged_mild` | 0,90 | Небажано |
| `discouraged_strong` | 0,70 | Суттєво небажано |
| `incompatible` | — (бар’єр G3) | Несумісно |

Агрегація кількох правил:
- `M_rot.mid` = добуток множників спрацьованих правил, обмежений знизу `discouraged_strong` і зверху `favorable`.

**Пропуски в історії.** Для кожного правила, умова якого залежить від років з пропуском або низькою надійністю, розглядаємо найгірше й найкраще допустиме заповнення:
- `M_rot.lo` — найгірший варіант (правило могло спрацювати);
- `M_rot.hi` — найкращий.

Наприклад, якщо історія порожня зовсім, `M_rot = [0.70, 1.05]`. Це однаково для всіх кандидатів, тож відносна позиція визначається GAEZ, але нижні межі чесно знижені.

**Калібрування.** Початкові значення — лише інструмент ранжування. Їх замінюємо:
- (а) відносними втратами врожаю з літератури або регіональних дослідів, на які посилається правило;
- (б) калібруванням на даних урожайності господарств (P2): регресія відносного врожаю на категорію попередника з фіксованими ефектами року й поля.

#### 5.5.3 `M_wx` — множник аномалії поточних умов посіву [ІНЖ. МОДЕЛЬ]

**Застосовується лише** до кандидатів, у яких `window.earliest ≤ as_of + nowcast_horizon` (за замовчуванням 30 днів). Тобто посів відбудеться в межах того, що вже відомо чи прогнозується. Для інших `M_wx = [1, 1, 1]`: їхні умови посіву ще невідомі, а середня очікувана умова вже закладена в GAEZ.

Ознака — **аномалія відносно норми того самого джерела**, а не абсолютне значення. Тому вона не дублює GAEZ, який описує середнє.

```
z_moist = перцентиль вологості верхнього шару ґрунту (0–7/7–28 см) на as_of
          відносно кліматології того ж дня року (1991–2020, той самий реаналіз)
z_prec  = перцентиль суми опадів за 30/60 днів до as_of
z_fcst  = частка днів прогнозу (до 16 днів) з опадами ≥ 5 мм у посівному вікні
signal  = комбінація за таблицею (без зважування):
          dry     — z_moist < P20 і z_prec < P20
          wet_ok  — z_moist > P60
          normal  — інакше
M_wx:  dry → [0.85, 0.90, 0.95];  normal → [0.97, 1.00, 1.03];  wet_ok → [1.00, 1.02, 1.05]
       даних немає → [0.85, 1.00, 1.05]   # пропуск розширює інтервал
```

Значення застосовуються лише до культур, для яких у каталозі позначено `establishment_moisture_sensitive: true`: озимі зернові, озимий ріпак, а також ярі, якщо їхній посів потрапив у горизонт. Такі позначки ставить агроном.

#### 5.5.4 Поріг мінімальної агропридатності

Кандидат із `Agro.hi < floor_agro` (за замовчуванням 0,40, що відповідає SI 40, межа класу «Medium») не потрапляє в рекомендації. Його показуємо в «оцінено, нижче порогу».

### 5.6 Крок 4 — агрономічні яруси

```
sorted = сортувати кандидатів за Agro.mid ↓
tiers = []
while sorted не порожній:
    leader = sorted[0]
    tier = [c ∈ sorted | c.Agro.hi ≥ leader.Agro.lo]   # інтервал перекривається з лідером
    tiers.append(tier); sorted -= tier
```

**Властивості.**
- Якщо інтервал культури повністю нижчий за інтервал лідера, вона потрапляє в нижчий ярус.
- Висока ціна не підніме культуру з нижчого ярусу. Цим забезпечено правило «ціна не перекриває непридатність».
- Широкі інтервали від пропусків роблять яруси більшими. Тоді більше рішень ухвалює економіка, а якщо її немає — агробал із прапорцем «близькі результати».

### 5.7 Крок 5 — економіка всередині ярусу

Для культури `c` з повною економікою (ціна + урожайність + витрати) рахуємо сценарну маржу за сценаріями `s ∈ {low, base, high}`:

```
Revenue_s(c) = Yield_s(c) [т/га товарної продукції] × Price_s(c) [грн/т, нормалізована основа]
Margin_s(c)  = Revenue_s(c) − Cost(c) [грн/га]
key(c) = (Margin_base(c), Margin_low(c))
```

**Правило впорядкування.**
1. У ярусі визначаємо підмножину `E` культур з повною економікою.
2. Позиції (слоти), які займають культури з `E` в агрономічному порядку ярусу, переставляємо між собою за `key ↓`.
3. Культури без повної економіки залишаються у своїх агрономічних слотах.

Так пропуск економіки не покращує й не погіршує позицію. Якщо в `|E| < 2` культур повна економіка, ярус лишається в агрономічному порядку.

Якщо є лише виручка без витрат, вона **не** впорядковує ярус. Виручка систематично завищує позиції культур із високими витратами (кукурудза із сушінням, цукровий буряк). Її показуємо як довідку.

### 5.8 Крок 6 — близькі результати й правила розв’язання нічиїх

- Усередині ярусу без економіки порядок такий:
  1. `Agro.mid ↓`;
  2. нижчий рівень ризику (§9);
  3. вища якість даних;
  4. диверсифікація родини: культура з родини, якої не було 2 останні роки, стоїть вище [ІНЖ. МОДЕЛЬ].
- Якщо `|Agro.mid(a) − Agro.mid(b)| < ε` (за замовчуванням 0,02), обидві культури отримують позначку `near_tie_with: [...]`. У тексті пишемо: «рівноцінні за агрономічною оцінкою; порядок визначила <причина>».

### 5.9 Крок 7 — стійкість рейтингу

Будуємо детерміновану сітку збурень `G`, тобто декартів добуток з обмеженням до ~100–300 варіантів:

| Вимір | Значення |
|---|---|
| Множники сівозміни | базові; −50 % відхилення від 1; +50 % відхилення від 1 |
| `M_wx` | базові; вимкнено |
| Кліматичний період GAEZ | HP0120; FP2140 ENSEMBLE SSP370 |
| Рівень агротехнологій | заявлений; альтернативний (якщо не заявлено явно) |
| Цінові сценарії | low / base / high |
| Витрати | ±15 % (якщо задані користувачем без діапазону) |
| Правило ярусів | перекриття інтервалів; `mid`-різниця ≤ 0,05 |

Для кожного `g ∈ G` перераховуємо повний конвеєр від кроку 3 до 7 (бар’єри не змінюються) і отримуємо рейтинг `r_g`. Для кожної культури:
- `p_top5` = частка `g`, у яких культура в топ-5;
- `rank_median`;
- `rank_range = [min, max]`.

| Мітка стійкості | Умова |
|---|---|
| `stable` | `p_top5 ≥ 0.8` і `max−min ≤ 2` |
| `sensitive` | не `stable`, але `p_top5 ≥ 0.5` |
| `unstable` | `p_top5 < 0.5` |

Для `sensitive` і `unstable` виділяємо вимір сітки, що найбільше змінює місце: шукаємо параметр, зміна якого переводить культуру за межу топ-5. Цей вимір показуємо в поясненні.

### 5.10 Крок 8 — фінальний відбір

```
final = []
for tier in tiers:
    for c in ordered(tier):
        if c.Agro.hi ≥ floor_agro and c.status ≠ CONDITIONAL_BLOCKING:
            final.append(c)
        if len(final) == 5: break
# умовні (CONDITIONAL) культури включаємо з позначкою «за умови підтвердження: ...»,
# але не більше 2 з 5, і лише якщо вони не нижче останньої безумовної за ярусом
```

Повертаємо від 0 до 5 культур. Якщо обґрунтовано доступні лише 3, повертаємо 3. Сенс не в тому, щоб заповнити 5 місць.

**Мітки для користувача** (не ймовірність успіху):
- `Agro` у відсотках: «Агрономічна оцінка 66–77 з 100»;
- ярус;
- стійкість.

### 5.11 Крок 9 — пояснення

## 6. Геопросторове отримання оцінки GAEZ

### 6.1 Перевірка геометрії та координат

1. Вхід: GeoJSON `Polygon` або `MultiPolygon` + явне поле `crs` (рядок `EPSG:xxxx`). Якщо `crs` відсутнє, повертаємо помилку, а не припускаємо 4326. RFC 7946 вимагає WGS84, але платформа може надсилати інше.
2. Перетворення в EPSG:4326 через `pyproj` з `always_xy=True`.
3. Перевірки:
   - діапазон lon/lat;
   - евристика переставлених координат: точка поза межами підтримуваних країн, але після перестановки потрапляє в них — тоді помилка `SUSPECTED_AXIS_SWAP`;
   - `shapely.is_valid`;
   - площа в локальній рівновеликій проєкції (LAEA з центром у центроїді) в межах `[0.1, 20000]` га (конфіг);
   - відсутність виродження.
4. Невалідна геометрія:
   - `shapely.make_valid` + перевірка, що зміна площі < 1 %. Тоді приймаємо з прапорцем `geometry_repaired`.
   - Інакше `INVALID_GEOMETRY` з описом (`explain_validity`).
5. Хеш геометрії = SHA-256 від нормалізованого WKB (орієнтація, округлення до 1e-7°). Це ключ кешу.

### 6.2 Визначення необхідних шарів

```
layers = for v in candidates: for wsim in assumed_wsim ∪ robustness_wsim:
           {SUX, SCX, SXX, SX1, YCX, WDC}(HP0120, AGERA5, HIST, v.gaez_code, wsim)
         ∪ {SUX}(FP2140, ENSEMBLE, {SSP126,SSP370,SSP585}, v.gaez_code, wsim∈{HILM,HRLM})
         ∪ {SXX30AS, SCX30AS, YCX30AS}(HP0120, AGERA5, HIST, ...)
```

Шлях до файлу будуємо з довідника `gaez_manifest` (§7.5). Його імпортуємо з лістингу бакета, а не конструюємо рядком наосліп. Якщо файлу немає в маніфесті, повертаємо `LAYER_NOT_AVAILABLE`, а не 404 у рантаймі.

### 6.3 Узгодження систем координат

GAEZ має EPSG:4326, поле після кроку 6.1 — теж. Растр **не перепроєктовуємо**: перепроєкція змінює значення комірок і їхню площу.

Частки покриття рахуємо в нативній сітці. Ваги комірок за площею враховують, що площа комірки ∝ cos(φ). Для поля розміром до кількох км ця поправка мізерна, але її рахуємо для коректності.

### 6.4 Перетин поля з комірками

Інструмент — `exactextract` (Python-біндинги): точна частка покриття кожного пікселя полігоном `f_i ∈ (0,1]`.

```
w_i = f_i × area(cell_i)           # м², з урахуванням широти
valid_i = value_i ≠ NoData (∧ для класів: value_i ∉ {0, 9})
coverage_valid = Σ w_i[valid] / Σ w_i
```

### 6.5 Отримання показників

**Числові** (SUX, SXX, SX1, YCX, WDC):
- `mean_w = Σ w_i·v_i / Σ w_i` лише по валідних;
- `min`, `max` по комірках з `f_i·area_i / area_field ≥ 0.1`;
- `n_cells`.

**Категоріальні** (SCX, SIX) **не усереднюємо**. Повертаємо розподіл:
- `share[k] = Σ w_i[class=k] / Σ w_i[valid]`;
- `dominant_class = argmax share`;
- `worst_class_with_share≥0.1`;
- частку класу 9 (вода) окремо, як «не застосовне».

**Результат на поле:** `GaezFieldValue`, див. §7.4.
- `field_area_ha`;
- `cell_area_ha_mean`;
- `field_to_cell_ratio`;
- `native_resolution_deg = 0.083333`, `native_resolution_km_approx`;
- `coverage_valid`;
- `per_cell = [{cell_id, f_i, value}]`.

### 6.6 Особливі випадки

| Випадок | Поведінка |
|---|---|
| Поле менше за комірку (типово: поле 100 га, комірка 5′ ≈ 5000 га на 49° пн. ш.) | Значення = значення комірки. У відповіді: «значення описує комірку ~6×9 км; поле займає {ratio:.1%} її площі». 30″ (~0,6×0,9 км ≈ 55 га на 49° пн. ш.) теж не описує ділянки поля |
| Поле перетинає кілька комірок | Середнє з вагами площі + min/max → інтервал `A` |
| Часткова відсутність даних | `coverage_valid` 0,8–1: норма; 0,5–0,8: `PARTIAL_COVERAGE`, розширений `A.lo`; < 0,5: культура «не оцінена» |
| Повна відсутність покриття | Для всіх культур < 0,5, тому `ABSTAIN` (`GAEZ_NO_COVERAGE`) |
| Різна роздільність шарів (5′ і 30″) | Кожен шар обробляємо в нативній сітці окремо. Значення не змішуємо в одне середнє, а використовуємо для інтервалу. Обидві роздільності вказуємо у відповіді |
| Некоректна геометрія | §6.1 |
| Поле на межі моря або водойми | Частка класу 9 знижує валідне покриття |

### 6.7 Вибір варіанта: вся комірка, поточні орні землі чи найкращий клас

- **`SXX`/`SIX` (вся комірка)** усереднює всі землі комірки: ліси, луки, схили, заплави. Для орного поля це **песимістичне** зміщення.
- **`SUX`/`SCX` (поточні орні землі)**. GAEZ припускає, що орні землі займають кращу частину розподілу придатності: при частці ріллі 20 % беруться найкращі 20 %. Для поля, яке вже є ріллею, це **найрепрезентативніше** припущення.
- **`YXX` (найкращий клас у комірці)** — верхня межа, **оптимістичне** зміщення.

**Рішення:**
- основа — `SUX`/`SCX`;
- `SXX` і `SX1` — індикатори неоднорідності: якщо `SUX − SXX` велике, комірка неоднорідна, і поле може бути гіршим за кращу частину;
- `YXX` використовуємо лише як довідку «стеля потенціалу».

Ці різниці показуємо у відповіді. Обрізання за полігоном не робить жоден варіант точнішим за його роздільність.

## 9. Неповні дані, ризики, помилки та відмова

### 9.1 Ризики (окремо від балу)

`RiskSummary` — набір індикаторів із рівнями `low/moderate/high/unknown`. У бал входить лише `M_wx` (поточна аномалія). Решта — для показу та розв’язання нічиїх.

| Індикатор | Розрахунок | Період |
|---|---|---|
| Ризик сходів | Аномалія вологості 0–28 см і опадів, прогноз опадів на 16 днів | Посівне вікно в горизонті |
| Ризик заморозку після сходів | Частота днів Tmin ≤ поріг культури в перші N днів після типової дати посіву, з кліматології 1991–2020 | Кліматологія |
| Ризик зимівлі (озимі) | Частота епізодів Tmin ≤ поріг без снігового покриву (`snow_depth`) | Кліматологія |
| Тепловий стрес у критичну фазу | Частота днів Tmax ≥ поріг у типове вікно цвітіння | Кліматологія |
| Тривалі сухі періоди | Частота сухих періодів ≥ 20 днів (P < 1 мм/день) у вегетацію | Кліматологія |
| Водна потреба культури | GAEZ `WDC` (мм) | Середній клімат |

Пороги культур — у каталозі з джерелом. Кліматологічні ризики **не штрафують бал**: GAEZ уже містить середній клімат. Вони показують мінливість між роками, якої GAEZ не відображає. Вони є тай-брейкером і обов’язковим попередженням.

### 9.2 Погода: мінімальні змінні та похідні

**Добові змінні:**
- `tmin`, `tmax`, `tmean`;
- `precip`;
- `et0` (FAO-56 від провайдера або власний розрахунок);
- `soil_moisture_0_7cm`, `soil_moisture_7_28cm`;
- `snow_depth`.

**Похідні:**
- суми опадів і водний баланс `P − ET0` за 30/60/90 днів та їхні перцентилі відносно норми;
- максимальний сухий період;
- GDD з базою культури;
- дати останнього весняного й першого осіннього заморозку;
- перцентиль вологості ґрунту.

**Типи даних і їхнє використання:**

| Тип даних | Для чого | Чого НЕ робимо |
|---|---|---|
| Спостереження / реаналіз (до `as_of`) | Поточний стан, норми 1991–2020 з того самого джерела | Не змішуємо норму одного джерела з поточним станом іншого |
| Короткий прогноз (≤ 16 днів, `issued_at ≤ as_of`) | Ризик у посівне вікно найближчих тижнів | Не описуємо ним наступні місяці |
| Сезонний прогноз (терцилі) | P2: ваги сценаріїв у сітці стійкості | Не використовуємо як детермінований прогноз |
| Кліматологія | Ризики, норми | — |

**Провайдер** [НЕ ПЕРЕВІРЕНО в межах цього документа: endpoints і ліцензії перевірити до P1]:
- Прототип: Open-Meteo. Один HTTP API для історії (реаналіз ERA5/ERA5-Land), прогнозу з вологістю ґрунту та сезонних даних. Для комерційного використання потрібен платний план.
- Production-кандидат для історії й норм: AgERA5 / ERA5-Land через Copernicus CDS. AgERA5 — те саме кліматичне джерело, що й базовий період GAEZ v5, тому дані узгоджені.
- Адаптер має єдиний інтерфейс `WeatherProvider.get(kind, lat, lon, vars, period, as_of)`.

**Заборона витоку з майбутнього:**
- кожен запис має `valid_time`, `issued_at` (для прогнозів) і `available_at`;
- адаптер відкидає все з `available_at > as_of`;
- реаналіз має затримку публікації (для ERA5 — дні), тому в бектесті `available_at = valid_time + latency`;
- прогнози для бектесту беруться лише з архіву випусків, а не з реаналізу «заднім числом».

**GAEZ і бектест.** `HP0120` охоплює 2001–2020. Бектест для сезонів ≤ 2020 використовує клімат, що включає роки після `as_of`. Для таких бектестів беремо `HP8100` або документуємо це обмеження.

Культуру не змінює | Валідація на полях з відомими культурами: матриця помилок класів сезонності |

- Порівнюємо лише однакову культуру й однакову фазу.
- Високий NDVI не є показником родючості.
- pH і доступні N-P-K із супутника не виводимо.

Загальні правила:
- Відсутнє значення ніколи не стає нулем: воно `None` + розширений інтервал або виключення з підмножини.
- Якість даних — окремий звіт `data_quality` з рівнями за джерелами та причинами. Загальний рівень = мінімум по **критичних** джерелах (GAEZ, вікна, історія). Він не домножується на бал.

### 9.5 Коли утримуватися від рекомендації

1. Немає валідного GAEZ-покриття.
2. Регіон не підтримується правилами або вікнами.
3. Жодна культура не досягає порогу.
4. Входи суперечливі: супутник показує поточну культуру в полі, а користувач стверджує, що поле вільне, і від цього залежать **всі** озимі кандидати. Тоді — `NEEDS_INPUT`, а не `ABSTAIN`.

| `price_value` | так | — |

### 10.2 Нормалізація

Порядок перетворень:
1. Одиниця → т.
2. Валюта → валюта запиту за курсом на `price_date`. Потрібна таблиця курсів, наприклад офіційний курс НБУ; її джерело фіксуємо.
3. ПДВ → без ПДВ за `vat_rate` із запису. Якщо ставки немає, ціну не використовуємо.
4. Основа поставки:
   - перетворюємо лише якщо користувач дав логістичні витрати грн/т від поля до точки поставки (`CPT порт → EXW поле = ціна − логістика`);
   - інакше в межах однієї рекомендації використовуємо ціни **однієї** основи; культури з іншою основою отримують `ECON_BASIS_MISMATCH` і не входять у `E`.
5. Якість: якщо `quality_basis` не збігається з типовою для культури, ставимо прапорець, без «довільної знижки».

Кожну нормалізовану ціну зберігаємо разом з ланцюжком перетворень.

### 10.3 Ціна на час збирання

**Ланцюжок пріоритетів для бази:**
1. Контрактна ціна користувача.
2. Форвардна ціна з `delivery_period` у місяці збирання.
3. Остання спотова ціна.

Поточна спотова ціна **завжди** позначається «поточна, не гарантована на час збирання».

**Сценарії low/high:**
- Емпіричні квантилі (P10/P90) відносної зміни ціни між місяцем `as_of` і місяцем збирання за попередні роки в таблиці, якщо історія ≥ 5 років.
- Інакше — фіксований конфігурований діапазон з позначкою «умовний діапазон» [ІНЖ. МОДЕЛЬ].

### 10.4 Урожайність і витрати

**Урожайність** для економіки, у порядку пріоритету:
1. Історія господарства на цьому полі або в господарстві для цієї культури (≥ 2 роки). Сценарії — мін/медіана/макс.
2. Сценарії, які вказав користувач.
3. Регіональна статистика (джерело та рік фіксуємо).
4. Немає — економіки для культури немає.

**GAEZ `YCX` / `YXX` не використовуються для економічного впорядкування.** Різні культури мають різний розрив між потенціалом і фактичним урожаєм. Без калібрування це спотворює порівняння, а довільний коефіцієнт «потенціал → факт» не вводимо.

Як довідку показуємо «виручку за потенціалом GAEZ» з чіткими застереженнями:
- `Y_товарна = Y_dm / (1 − m)`, де `m` — вологість з таблиці модуля VII (наприклад, 13 % для пшениці). Це фізичне перетворення сухої речовини на товарну вологість, а не поправка на фактичний урожай.
- Для `SUB` (цукровий буряк) GAEZ виражає урожай **у цукрі**, тож перерахунок у тонни коренеплодів без коефіцієнта вилучення неможливий. Довідку не показуємо.
- Для олійних культур одиницю перевіряємо за Додатком 4-6 перед використанням [НЕ ПЕРЕВІРЕНО для кожної культури].

**Витрати:**
- Мінімальний спосіб — одне число грн/га на культуру + опційно сушіння грн/т і логістика грн/т.
- Поле `includes[]` фіксує, що враховано.
- Без витрат — режим лише з виручкою, яка **не впорядковує** культури.
- P2: регіональні шаблони витрат з версією та датою, які користувач підтверджує або редагує.

### 10.5 Термінологія у відповіді

| Термін | Визначення |
|---|---|
| «Ціна, грн/т» | Нормалізована ціна з датою |
| «Сценарна виручка, грн/га» | Урожайність × ціна, сценарії |
| «Витрати, грн/га» | Тільки введені користувачем |
| «Сценарна маржа, грн/га» | Виручка − введені витрати. **Не** «прибуток»: не враховано податки, оренду (якщо не введено), фінансування тощо |

```python
def prepare_field(field_id, as_of) -> FieldFeatureSnapshot:            # worker, асинхронно
    f = platform.get_field(field_id)
    geom = geo.validate_and_normalize(f.geometry, f.crs)               # §6.1, може кинути InvalidGeometry
    region = geo.region_of(geom)
    catalog = rules.catalog(region)                                    # підтримувані варіанти
    layers = gaez.required_layers(catalog, wsim_all=True)              # §6.2
    gaez_vals = {l: cache.get_or(geom.hash, l, lambda: geo.extract(geom, gaez.open(l))) for l in layers}
    hist = history.normalize(platform.get_history(field_id))           # уніфікація кодів, сезонів, надійностей
    sat = satellite.qc_and_features(platform.get_indices(field_id, until=as_of), hist, as_of)
    hist = history.apply_satellite_consistency(hist, sat)              # змінює лише reliability
    wx_clim = weather.climatology(geom.centroid, 1991, 2020)           # кешується назавжди
    wx_now = weather.state_and_forecast(geom.centroid, as_of)          # available_at <= as_of
    return snapshot.store(field_id, geom, region, gaez_vals, hist, sat, wx_clim, wx_now,
                          provenance=collect_provenance())

def recommend(req: RecommendationRequest) -> RecommendationResult:     # чиста функція над snapshot
    snap = snapshot.latest_valid(req.field_id, req.as_of_date) or enqueue_prepare_and_return_202()
    R = rules.load(version="active")                                   # каталог, вікна, правила, множники
    trace = Trace()

    # 0. перевірка входів і режиму
    if not req.target_season: return needs_input("target_season")
    if not R.region_supported(snap.region): return abstain("REGION_NOT_SUPPORTED")

    # 1. кандидати
    cands = [v for v in R.catalog(snap.region)
             if sowing_window_intersects(v, snap.region, req.as_of_date, req.target_season)]

    evals, excluded, not_eval = [], [], []
    for v in cands:
        gv = gaez_for(v, snap, req.management)                         # SUX, SCX, ... за wsim
        # 2. бар'єри
        g = run_gates(v, req, snap, R, gv, trace)                      # G1..G5 у порядку
        if g.excluded: excluded.append(g); continue
        if g.not_evaluable: not_eval.append(g); continue
        # 3. інтервали
        A   = a_gaez_interval(gv, trace)                               # §5.5.1
        Mr  = m_rot_interval(v, snap.history, R.rotation, trace)       # §5.5.2
        Mw  = m_wx_interval(v, snap.weather, req.as_of_date, R, trace) # §5.5.3
        agro = Interval.product(A, Mr, Mw)
        if agro.hi < R.params.floor_agro:
            trace.add("BELOW_FLOOR", v); below.append(v); continue
        evals.append(CandidateEvaluation(v, g, A, Mr, Mw, agro,
                     risk=risk_indicators(v, snap, gv), dq=data_quality(v, snap, gv)))

    if not evals: return abstain("NO_CANDIDATE_ABOVE_FLOOR", excluded, not_eval)

    # 4–6. яруси, економіка, нічиї
    def rank(evals, params):
        tiers = build_tiers(evals, rule=params.tier_rule)              # §5.6
        ordered = []
        for t in tiers:
            t = sorted(t, key=lambda e: (-e.agro.mid, e.risk.level, -e.dq.level, -e.diversification))
            econ = [e for e in t if econ_complete(e, req, snap.prices, params)]
            if len(econ) >= 2:
                slots = [i for i, e in enumerate(t) if e in econ]
                by_margin = sorted(econ, key=lambda e: (-e.margin(params).base, -e.margin(params).low))
                for i, e in zip(slots, by_margin): t[i] = e
            ordered += t
        return ordered

    base = rank(evals, R.params)

    # 7. стійкість
    grid = robustness_grid(R.params, req, snap)                       # детермінована сітка
    ranks = {g.id: rank([recompute(e, g) for e in evals], g) for g in grid}
    stability = summarize_stability(base, ranks)                       # p_top5, діапазон, драйвер

    # 8. фінальний відбір
    final = select_up_to_5(base, stability, R.params, trace)

    # режим
    mode = decide_mode(final, req, snap, stability)                    # FULL/AGRO_ONLY/LIMITED/NEEDS_INPUT
    # 9. пояснення
    texts = explain.render(final, excluded, trace, lang=req.options.language)
    return persist(RecommendationResult(..., provenance=Provenance(
        computed_at=now(), as_of=req.as_of_date, algorithm_version=ALGO_VERSION,
        rules_version=R.version, gaez_layers=[l.meta for l in used_layers],
        weather_sources=snap.weather.provenance, price_rows=used_price_ids,
        assumptions=collected_assumptions, robustness_grid_hash=hash(grid))))
```

**Відтворюваність.** `recommend` не звертається до мережі. Повторний виклик із тим самим `snapshot_id` і `rules_version` дає побітово однаковий результат. Перевіряємо це тестом.

**Ресурси.**
- Ранжування: десятки кандидатів × ~100–300 варіантів сітки = десятки тисяч простих арифметичних операцій. Вимірювано невеликий час на CPU, але цільовий SLA визначимо після вимірювань.
- Перша підготовка нового поля залежить від зовнішніх API (платформа, погода) і першого читання COG. Тому вона асинхронна і може тривати значно довше.

## 12. План перевірки якості

### 12.1 Геопросторова частина

- **Синтетичні растри.** Відомі значення в шаховому порядку; поля:
  - всередині однієї комірки;
  - на перетині 4 комірок у пропорціях 25/25/25/25 та 70/10/10/10;
  - з дірками;
  - MultiPolygon;
  - на межі NoData.

  Очікувані середні рахуємо аналітично. Перевіряємо, що класи не усереднюються.
- **Реальні шари.** Для 20 контрольних точок порівнюємо витяг із значенням у веб-платформі GAEZ v5 (ручна звірка).
- Перевірка CRS (поле в EPSG:32636 і EPSG:4326 дає однаковий результат) і детектор переставлених осей.

### 12.2 Одиниці та NoData

- Тест-маніфест: для кожної змінної очікувані `dtype`, `nodata`, діапазон (SXX ∈ [0, 10000], SIX ∈ [0..9]). Під час імпорту файл, що не відповідає маніфесту, відхиляємо.
- Property-тест: жодне `NoData` не потрапляє в середнє; `coverage_valid` ∈ [0,1].

### 12.3 Агрономічні правила

- Схемна валідація YAML/CSV у CI: обов’язкові `source`, `version`, `regions`. Правило `approved` без `verified_by` — помилка.
- Таблиця-оракул від агронома: 30–50 пар «попередник → кандидат» з очікуваною категорією. Тест порівнює.
- Детектор конфліктів: два правила для однієї пари з протилежними наслідками.

### 12.4 Стійкість і чутливість

- Звіт по кожному прогону: `p_top5`, діапазони.
- Глобальний аналіз на вибірці ≥ 100 полів: які параметри найчастіше змінюють топ-5. Ці параметри калібруємо першими.
- Монотонність (property-тести):
  - підвищення ціни культури не погіршує її місце;
  - зниження `A` не покращує;
  - додавання пропуску не покращує.

### 12.5 Пропуски

- Для кожного рядка таблиці §9.4 — сценарний тест з очікуваним режимом і повідомленням.
- Інваріант «пропуск не покращує позицію»: видалити будь-який вхід → `lo` культури не зростає, а її місце не покращується відносно культур, яких пропуск не стосується.

### 12.6 Відсутність даних з майбутнього

- Кожен адаптер має тест: запит із `as_of = T` не повертає записів з `available_at > T`.
- Канарейка: у фікстуру вставляємо запис з `available_at = T+1` з аномальним значенням; результат не має змінитися.
- Бектест-режим: прогнози лише з архіву випусків; GAEZ — `HP8100` для сезонів ≤ 2020 (або документоване обмеження).

### 12.7 Обґрунтованість (з агрономом)

**Сліпа експертна оцінка.** 50–100 полів різних регіонів. Агроном бачить вхідні дані й список системи (без її пояснень) і оцінює:
- (а) прийнятність кожної культури (так / умовно / ні з причиною);
- (б) чи пропущено очевидну культуру.

Метрики:
- частка неприйнятних рекомендацій;
- частка пропусків;
- узгодженість між двома агрономами.

**Перевірка пояснень.** Агроном перевіряє, що кожна причина в тексті відповідає даним.

### 12.8 Що можна перевірити без вирощування альтернатив і що — ні

| Можна перевірити зараз | Потрібні польові дані / спостереження |
|---|---|
| Правильність обчислень, одиниць, геообробки | Чи дає рекомендована культура вищий фактичний результат, ніж альтернативи |
| Відповідність правилам і експертній думці | Калібрування множників `M_rot`, `M_wx` |
| Стійкість і монотонність | Модель урожайності, що замінить GAEZ-потенціал |
| Чи система не рекомендує культуру, яка на цьому полі в історії стабільно провалювалася (за даними урожайності) | Причинний ефект: смугові досліди (strip trials) або тривале спостереження за полями, де рекомендацію виконали чи не виконали, з контролем на рік і регіон |
| Зв’язок `A_gaez` з регіональною статистикою: кореляція придатності з часткою посівів і урожайністю культури в районах | — |

**Збіг із вибором фермера** рахуємо лише як описову метрику «узгодженості», а не як точність. Фермер міг обрати культуру з причин, яких немає в моделі, або помилитися.

### 12.9 Перевірка користі кожного джерела (абляція)

Послідовні конфігурації на одній вибірці полів:

```
C0: GAEZ + бар'єри + правила сівозміни
C1: C0 + погода (M_wx + ризики)
C2: C1 + супутник (надійність історії)
C3: C2 + економіка в ярусах
```

Для кожного переходу `Ck → Ck+1` вимірюємо:
1. **Зміну рейтингу:** Kendall τ, частку полів зі зміною топ-3.
2. **Якість за експертом:** парне сліпе порівняння списків Ck і Ck+1 агрономом. Частка, де новий список кращий / гірший / рівний.
3. **Ретроспективну перевірку для погоди:** на полях з відомими провалами сходів (історія + супутник) чи `M_wx` (з даними лише до `as_of`) понижував такі культури частіше, ніж на полях без провалів.
4. **Для супутника:** на навмисно зіпсованих записах історії (підмінена культура) частка виявлених невідповідностей і частка хибних тривог.
5. **Для економіки:** чи потрапляє реалізована ціна на час збирання в діапазон low–high (покриття сценаріїв) на історичних даних таблиці цін.

Джерело, яке не покращує метрику 2 і не має окремого підтвердження (3–5), лишається в режимі «лише показ».

## 14. Невизначеності, що залишилися

1. **Підтипи культур у GAEZ v5** [НЕ ПЕРЕВІРЕНО].
   - RES05 не розділяє озимі та ярі.
   - Підписи `HWHE`/`WWHE` у довіднику вимірів суперечать Додатку 4-1.
   - У вибірці центральної України `WHEA` = `SWHE`.
   - До з’ясування озимі варіанти мають `gaez_match = parent_crop`.
2. **Одиниці врожайності окремих культур** (олійні, цукрові) для RES05 `Y*` — перевірити за Додатком 4-6.
3. **Повний перелік періодів для шарів 30″.** Перша сторінка лістингу містить лише HP0120 і HP8100. Також не перевірено, чи існують `L*LM` для майбутніх періодів.
4. **Ліцензії окремих наборів.** CC BY 4.0 підтверджено для одного запису каталогу; для решти використаних наборів — перевірити.
5. **Поведінка `SUX`** у комірках, де за GAEZ немає ріллі (NoData чи 0) — перевірити на реальних полях.
6. **Погодні провайдери:** точні endpoints, змінні вологості ґрунту, затримки публікації, комерційні умови.
7. **Значення множників, порогів і `floor_agro`.** Усі значення — інженерні заглушки до калібрування.
8. **Наявність історії цін** достатньої довжини для емпіричних сценаріїв.

## 15. Питання, відповіді на які суттєво змінять рішення

1. **Регіон запуску.** Лише Україна (або одна-дві області) чи кілька країн? Від цього залежать каталог культур, обсяг правил і посівних вікон, вибір провайдера погоди та цін.
2. **Хто наповнює й підписує правила сівозміни та посівні вікна?** Чи є агроном у команді або партнер з регіональними рекомендаціями? Без цього правила лишаються `draft`, і рейтинг спиратиметься майже лише на GAEZ.
3. **Чи має платформа урожайність і витрати господарств?** Якщо так, економіка в ярусах стає основним режимом, а модель урожайності (P2) — реалістичною. Якщо ні, основний режим — `AGRO_ONLY`.
4. **Яка основа цін у таблиці** (EXW / CPT порт, з ПДВ чи без, за якими регіонами) і чи зберігається історія цін? Від цього залежить, чи можна порівнювати культури економічно без логістичних витрат користувача.
5. **Для кого рекомендація:** для агронома господарства (детальні інтервали, правила) чи для власника без агрономічної підготовки? Це змінює формат пояснень, але не механізм.
