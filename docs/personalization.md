# Персоналізація рекомендацій

Типовий профіль `personalized` доповнює GAEZ історією культур, NDVI/NDMI,
спектральними знімками, місцевими спостереженнями та датованими прогнозами.
`gaez_baseline` і `validated` залишаються окремими доступними профілями.

Спочатку оцінюються всі кандидати, потім вибирається до п'яти. Порядок:
найвищий пріоритет ризику 0–3, кількість ризиків/невідомих перевірок, нижня та
центральна придатність GAEZ. Пропуск потрібних даних — `unknown` із пріоритетом
правила, а не сприятливий результат. `agro_score` лишається індексом GAEZ;
`personalization.assessments` пояснює зміну порядку. Ризик не перетворюється
на вигаданий відсоток втрати врожаю. Політика не калібрована на реальних полях,
тому результат залишається `LIMITED`.

## Дані господарства

Маршрути мають префікс `/v1/fields/{field_id}`; для кожного є `GET`.

| Метод / маршрут | Вміст |
|---|---|
| `PUT /history` | Історія `crop`, `season_year`/`year`, роль, надійність, дати збирання |
| `POST /indices` | Один `SatelliteSeries` з `index=NDVI` або `NDMI`; імпортуйте кожен окремо |
| `POST /images` | Геоприв'язаний маскований GeoTIFF у JSON |
| `PUT /weather` | Координати джерела та щоденні timestamped погодні записи |
| `PUT /personalization` | Політика господарства, дати посіву; також можна передати індекси/погоду |

У `POST /v1/recommendations` можна додати об'єкт `personalization` із
`indices`, `weather`, `policy`, `sowing_dates`. Явно передані параметри мають
пріоритет перед збереженим `/personalization`; окремі імпорти — запасні джерела.
`policy:null` вибирає типову політику. Для озимих рік посіву дорівнює року
врожаю мінус один; для ярих/літніх — року врожаю.

Адресу, формат і авторизацію вашого зовнішнього API треба надати для його
підключення. Автоматичного опитування вашої платформи/станції зараз немає:
робочий шлях — імпорт через API або файл. Точність джерела не гарантується
самою наявністю координат.

## Знімки та індекси

Попередній контракт `SatelliteSeries` збережено. Для персоналізації достатньо
`mean`, `date/acquired_at/available_at`, `valid_pixel_fraction` та метаданих
сенсора, роздільності, версії обробки. `median/p10/p90/std` перевіряються, коли
надані. NDMI характеризує вологість рослинності, а не є прямим виміром вологості
ґрунту. Високий NDVI сам собою не визначає кращу наступну культуру.

NDVI й NDMI обробляються незалежно. `delta` порівнює різні дні одного сенсора,
версії обробки й роздільності. Перепублікація одного дня не є зміною вегетації.
Ваші готові індекси мають пріоритет над результатом знімка на той самий день.

Контракт знімка (`bands`, `scale`, `clear_values` нижче — умовні приклади):

```json
{
  "image_id": "scene-001",
  "data_base64": "<base64 of self-contained GeoTIFF>",
  "acquired_at": "2026-10-25T10:00:00Z",
  "available_at": "2026-10-26T06:00:00Z",
  "sensor": "YOUR_SENSOR",
  "processing_version": "your-pipeline-v1",
  "bands": {"red": 1, "nir": 2, "swir": 3, "quality": 4},
  "scale": 0.0001,
  "offset": 0,
  "clear_values": [1]
}
```

Підтримано `red/nir/swir` або готові `NDVI/NDMI` плюс обов'язковий канал якості.
Растр має CRS, геоприв'язку та узгоджену сітку каналів. Статистики зважуються
площами точних перетинів пікселів із полем у рівноплощинній проєкції. NoData,
хмари, некоректні знаменники вилучаються. Покриття включає всю площу поля,
навіть частину поза знімком. Растри не пересемплюються.
Максимум файла — 10 МіБ, вікна — 250 тис. пікселів; для більших вікон передайте
грубший растр або готові статистики. `GET /images` не повертає бінарні дані.
RGB-фото/PNG без спектральних каналів не дозволяє обчислити NDVI/NDMI;
класифікатора культур чи хвороб із таких фото немає.

Формули: NDVI `(NIR-red)/(NIR+red)`, NDMI `(NIR-SWIR)/(NIR+SWIR)`.
Джерело NDMI: [USGS](https://www.usgs.gov/landsat-missions/normalized-difference-moisture-index).

## Погода

`PUT /weather` приймає `latitude`, `longitude`, необов'язкові `resolution_m`,
`max_distance_km` (типово 25) і `records`. Запис:

```json
{
  "valid_time": "2026-10-25T00:00:00Z",
  "available_at": "2026-10-26T06:00:00Z",
  "kind": "observation",
  "provider": "YOUR_STATION",
  "values": {"tmin": 5, "tmax": 16, "precip": 2.5, "et0": 1.8,
             "soil_moisture_0_7": 0.25}
}
```

Це синтетичні значення: температура °C, добові опади й ET0 у мм, вологість
м³/м³. Відсутнє вимірювання — пропущений ключ або `null`, а не нуль.
`kind`: `observation/reanalysis/forecast/climatology`. Прогноз обов'язково має
фактичний `issued_at`; час випуску не вигадується. Перевіряються відстань,
фізичні діапазони, доступність та свіжість.

Доступні показники правил:

- `NDVI.mean`, `NDMI.mean`, `NDVI.delta`, `NDMI.delta`;
- `weather.precip_7d`, `weather.precip_30d`, `weather.balance_30d` (опади мінус ET0,
  не повна модель водного балансу ґрунту);
- `weather.soil_moisture`, `weather.tmin_7d`, `weather.tmax_7d`;
- `forecast.tmin_7d`, `forecast.tmax_7d`, `forecast.precip_7d`.

Спостереження пріоритетніші за реаналіз. Вікна не змішують провайдерів;
неповні суми залишаються невідомими. Прогнозні 7 днів належать одному випуску.
Поточні показники впливають лише в межах `horizon_days` перед посівом (до 30
днів; для прогнозу до 7). Сьогоднішні умови не прогнозують наступний сезон.
`SIVAY_WEATHER_PATH` підтримує цей самий контракт точкового експорту.

## Сівозміна й правила

`rules/personalization.json` перевіряє повторний посів та експериментальний
інтервал повернення соняшнику. Джерело останнього:
[University of Minnesota, Alternative Crops](https://organicriskmanagement.umn.edu/sites/organicriskmanagement.umn.edu/files/2021-02/alternative_crops.pdf).
Це зарубіжний матеріал, не затвердження правил для України. Чернеткові правила
в `rules/rotation` не отримують статусу затверджених.

Політика господарства задає `min_return_years`, `avoid_predecessors` і правила
`metric/operator/threshold/priority/horizon_days/crops/source/explanation_uk`.
Селектор `wheat_winter` стосується лише озимої пшениці, `wheat` — обох
варіантів, `*` — всіх культур. Невідомі роки не доводять дотримання сівозміни.

Типова політика **не містить універсальних погодних/NDVI/NDMI порогів**.
Дані обробляються та показуються в результаті; відсутні правила зазначаються
в `requests_for_input`. Щоб ці дані змінювали рейтинг, задайте правила
господарства. `examples/personalization.json` — синтетичний приклад структури,
його пороги й дати не є порадою та не підключаються автоматично.

## Відтворюваність

Результат містить виміри, джерела, SHA-256 знімків, версію політики, перевірки
та пояснення зі слідом обчислення. Оновлення джерел/політики створює новий
snapshot. Replay старого результату не читає нові джерела. Імпортовані пізніше
дані не потрапляють до історичного snapshot, попри стару дату спостереження.
CLI `app.validation` підтримує профіль `personalized`; аудит перевіряє часові
мітки нових джерел. Прогнозні snapshot вимагають окремої перевірки архіву.

Тести: `tests/test_personalization.py` — зміна рейтингу й складу топ-5,
GeoTIFF/маска/покриття, обидва індекси, сумісність версій, погодні вікна,
часовий горизонт, сівозміна, HTTP-імпорт, оновлення й незмінний replay без DEMO.
