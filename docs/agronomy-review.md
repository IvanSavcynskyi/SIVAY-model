# Пакет агрономічної перевірки

Обсяг MVP, підтверджений користувачем: уся Україна (`UA`). Окремий профіль `gaez_baseline` працює без агронома й показує лише умовний потенціал GAEZ; повний агрономічний профіль потребує схвалення правил. Каталог містить 12 варіантів культур. Коди GAEZ перенесено з дизайну §5.3; вони не є підтвердженням придатності культур для області. Родини й сезонність є чернеткою класифікації. Чутливість до вологи та товарні специфікації не підтверджені й залишені `null`.

`rules/sowing_windows/ua.csv` містить рядок на кожний варіант, але всі дати й тривалості залишено порожніми. Числа з демонстраційного прикладу дизайну не перенесено в production. `rules/multipliers.yaml` не містить числових припущень: усі значення `null`, статус `draft`. Два правила сівозміни з дизайну §7.6 також залишені `draft`.

`rules/oracle.csv` містить 40 пар «попередник → кандидат» для сліпої експертизи. `expected_effect` навмисно порожній. Це перелік питань експертові, а не 40 перевірених відповідей. Чернетки не є агрономічною валідацією MVP.

Експерт має для кожного схваленого запису зазначити джерело (`source_ref` або `source_url` у CSV; `source.ref` або `source.url` у YAML), ім'я відповідального `verified_by`, дату `verified_at`, та перевести `status` у `approved`. Валідатор перевіряє заповнення цих полів; достовірність джерела та повноваження експерта перевіряються людиною.

Потрібно підтвердити:

1. Регіон, перелік культур, ботанічні групи, сезонність та чутливість сходів до вологи.
2. Межі й оптимальні дати посіву для кожного варіанта, мінімальні строки підготовки та завчасності.
3. Умови та категорії наслідків сівозміни, зокрема інтервали повернення.
4. Значення множників та порога агропридатності з обґрунтуванням калібрування.
5. Очікувані наслідки для 40 пар у таблиці-оракулі; за потреби уточнити рік, вологозабезпечення та технологію в `notes`.

Програмний доступ: `from app.rules import load_rules; rules = load_rules("rules")` повертає спільний `domain.RuleSet` із збереженням статусів. Для інспекції та перевірки готовності `load_rule_bundle("rules")` повертає всі записи; його `active_catalog`, `active_windows`, `active_rotation`, `active_multipliers` повертають лише `approved`. `readiness_issues("UA")` показує блокери. Поки немає схвалених вікон, production не має підстав формувати календарні рекомендації й повинен запросити їх або утриматися від оцінки. Частково підтверджений набір числових параметрів цілком вимкнений до завершення перевірки.

Зміна YAML/CSV, включно з таблицею експертизи, змінює SHA-256 та `bundle.version`. Production-завантажувач відхиляє будь-який запис `demo`. Параметр `allow_demo=True` дозволяє лише інспекцію тестового пакета і не робить `demo` активним.

Для синтетичного наскрізного тестування є `rules/demo/`: `load_rules("rules/demo", allow_demo=True)` повертає `RuleSet` із `demo=true` та статусами `demo`. Рушій може застосовувати його виключно в явно ввімкненому демонстраційному режимі. Жоден демонстраційний запис не позначено як `approved`, жодного підпису агронома не створено. Множники, поріг, горизонт та близькі оцінки відповідають демонстраційним параметрам дизайну §5 і §8. Календар пшениці та ріпаку — приклад §7.6; календарі інших культур, інтервал повернення соняшнику, товарні ключі та строки свіжості цін 30/90 днів є синтетичними тестовими даними. Вони не є агрономічними твердженнями. Редагування вкладеного `rules/demo/` не змінює версію production-пакета.

Команда валідації: `python -m app.rules rules`. Для тестового пакета: `python -m app.rules rules/demo --allow-demo`. Успішна синтаксична перевірка чернетки не означає готовності до агрономічних рекомендацій; поле `readiness` містить блокери схвалення.

Поведінка рушія для `draft`: жодного бар'єра чи штрафу. Якщо рушій може обчислити умову чернетки, він може записати `RULE_DRAFT_WOULD_FIRE`; правило з невідомим числовим параметром не оцінюється. Створення таких trace-подій належить рушію ранжування.
