# Зважений розрахунок та автоматичні джерела

Алгоритм `personalized-2.0.0`: карта GAEZ → перевірки сівозміни → зважені
погодні/індексні поправки → до п'яти кандидатів. Порядок перевірок сівозміни
збережений; зважений бал упорядковує кандидатів усередині однакового рівня
обмежень сівозміни. Вища придатність не компенсує виявлений більший ризик
сівозміни.

Публічний `results[].score` містить зважений індекс 0–1. Це не ймовірність,
не прогноз урожайності й не частка втрати врожаю. Базовий GAEZ зберігається
окремо. Повний внутрішній результат містить `ranking_score` та
`personalization.weighted`: базу, внесок кожного правила, групові коефіцієнти,
підсумок і невизначеність. Короткі пояснення залишаються в публічному API.

## Формула

Для правила задаються поріг `threshold`, максимальна поправка `weight` у 0–1
та необов'язковий `full_risk_at`, на якому поправка досягає максимуму.
Для `lt` повний ризик має бути нижче порога; для `gt` — вище.

```
severity_i = clip((value_i - threshold_i) / (full_risk_at_i - threshold_i), 0, 1)
penalty_i  = weight_i × severity_i
penalty_g  = max(penalty_i для правил групи g)
score      = GAEZ × ∏(1 - penalty_g)
```

Без `full_risk_at` правило бінарне: порушення дає `severity=1`, відсутність
порушення — 0. `weight=0` вимикає числовий вплив. Пріоритет правила збережено
для пояснення ризику, але погода й індекси тепер сортуються за зваженим балом.

Групи:

- `moisture`: опади, P−ET0, вологість ґрунту, NDMI;
- `temperature`: мінімальні/максимальні температури;
- `vegetation`: NDVI.

`group` можна задати явно. Усередині групи використовується максимальна
поправка: повторення правила або корельованого виміру не множить один ризик
кілька разів. Групові коефіцієнти перемножуються. Додавання поправок не може
підняти індекс вище GAEZ.

Приклад: GAEZ 0.8, групова поправка зволоження 0.1, температурна 0.15:
`0.8 × 0.9 × 0.85 = 0.612`. Це **61.2 бала зі 100**, а не прогноз урожаю.

Коли потрібне вимірювання відсутнє, його інтенсивність представлена інтервалом
`[0, 1, 1]`: нижній і центральний бали враховують максимальну задану поправку,
верхній зберігає нейтральний потенціал. Центральний бал тут консервативний,
не математичне сподівання. Видалення даних не покращує нижню або центральну
оцінку. Ваги не перенормовуються за наявними джерелами.

## Стартова політика

`rules/personalization.json` версії 2 містить явні **експериментальні** правила:
атмосферний баланс P−ET0, чутливість кукурудзи до заморозків, зниження NDMI/NDVI.
Стартові ваги, межі плавного переходу та NDVI-поріг рослинного покриву є
інженерними параметрами, не результатом навчання чи регіональної експертизи.
Їх наведено у файлі разом із походженням і обмеженнями.

NDMI характеризує вологість рослинності, а P−ET0 не є повною моделлю води в
кореневій зоні. Спад NDVI може бути наслідком збирання або фази розвитку.
Тому індексні поправки обмежені й перевіряють наявність рослинного покриву;
для відповідального агрономічного застосування потрібне калібрування на
місцевих даних і перевірка контексту фази розвитку. Статус відповіді лишається
`limited`. Замінити політику можна через `/fields/{id}/personalization`.

Приклад одного правила:

```json
{
  "id": "farm.water",
  "crops": ["wheat_winter"],
  "metric": "weather.balance_30d",
  "operator": "lt",
  "threshold": 0,
  "full_risk_at": -60,
  "weight": 0.15,
  "group": "moisture",
  "horizon_days": 14,
  "source": "EXAMPLE ONLY: replace with farm policy",
  "explanation_uk": "Опади нижчі за еталонну випаровуваність."
}
```

Дати посіву передаються в `personalization.sowing_dates`. Без них поточні
умови не можна прив'язати до майбутнього посіву; результат явно запитує дати.
За межами `horizon_days` поточна поправка не застосовується. Для прогнозу
межа не перевищує 7 днів; сьогоднішня погода не прогнозує наступний сезон.

## Отримання відкритих даних за полігоном

Для поточного дня профіль `personalized` автоматично збирає відсутні джерела:

1. Open-Meteo Historical Weather API: щоденна історія ECMWF IFS за останні
   35 днів до T−2, включно з температурою, опадами, ET0, доступною вологістю.
2. Open-Meteo Single Runs API: конкретний випуск ECMWF IFS, наступні дні.
   Початок циклу та реальний час отримання зберігаються окремо.
3. Earth Search: Sentinel-2 L2A Collection 1 за полігоном за останні 30 днів.
   Читаються тільки вікна каналів red/NIR/SWIR/SCL у COG; радіометричні scale
   та offset беруться з метаданих. Red/NIR усереднюються на сітку SWIR,
   маска якості використовує nearest-neighbor. NDMI не видається за дані 10м.
   Вибирається до трьох різних дат; перекриття тайлів одного дня не є трендом.

Провайдер погоди має роздільність близько 9 км: це модель для місцевості, не
вимір станції на полі. Для індексів використовуються точні межі поля, площі
перетинів пікселів, маска хмар/NoData, контроль покриття та свіжості.

Ручні дані мають пріоритет. Джерела оновлюються незалежно й кешуються в БД
разом із геометрією поля. Зміна геометрії або закінчення TTL запускає оновлення.
При помилці доступні джерела зберігаються, а відсутні показники отримують
невизначеність. Під час replay мережа не викликається.

```
SIVAY_AUTOMATIC_SOURCES_ENABLED=true
SIVAY_AUTOMATIC_WEATHER_TTL_SECONDS=3600
SIVAY_AUTOMATIC_INDICES_TTL_SECONDS=21600
```

Перший запит може потребувати завантаження вікон знімків. Для попередньої
підготовки підтримується наявний `/prepare` із worker. Для роботи без мережі
встановіть `SIVAY_AUTOMATIC_SOURCES_ENABLED=false`; імпортовані дані працюють.
Для історичної дати нові завантаження не виконуються: сьогодні отримані дані
не підміняють архів доступності. Для історичних рекомендацій потрібні раніше
зібрані snapshot/джерела.

Відкритий API Open-Meteo має обмеження некомерційного використання; для
комерційного розгортання потрібен відповідний доступ провайдера або власний
сервіс. Публічні Sentinel COG доступні без AWS-акаунта.

## Перевірки

`tests/test_weighted.py`: точна арифметика, насичення поправки, обидва напрямки
порогів, нейтральні правила, інтервали пропусків, властивості монотонності,
обмеженість балу, захист від дублювання групових сигналів, зміна рейтингу.

`tests/test_automatic_sources.py`: прив'язаний випуск прогнозу, часові мітки,
реальне читання контрольованих растрів із різними сітками та offset, кеш,
історичні обмеження, HTTP-запит без ручного імпорту та незмінний replay.

Для невеликої живої перевірки з реальними даними і **синтетичним планом посіву**:

```sh
.venv/bin/python scripts/smoke_personalized.py --output /tmp/sivay-weighted-live.json
```

План у цій команді потрібний для перевірки коду; він не є порадою щодо дат
посіву. Скрипт використовує тимчасову БД і не змінює господарські записи.
